# Workspace read queue assessment

Assessment only, 2026-10-23. No implementation or runtime proof is authorized by this note.

## Recommendation

Keep scheduler turns and mutations serialized. A small, explicit set of SQL-only GET handlers can plausibly run outside that queue after the existing workspace checks and synchronous initialization. The smallest useful candidate is `GET /api/event-history` plus `GET /api/cursor`. Prove it against the real Workspace in workerd before changing the runtime. Do not bypass the queue for every GET or HEAD.

Keep `/api/runs`, `/api/loopies`, enriched run snapshots, event detail and SSE setup, cloud status, daemon status, and artifact exports on the current path for the first change. Some can move later, but their present implementations have different consistency requirements. This first candidate would address one measured route, event history. It would not fix the measured runs and loopies paths or remove mutation latency behind provider calls.

There is no need for a persistence plugin system, another scheduler, a second store connection, or a new service abstraction to test this proposal. Do not shorten scheduler critical sections around external calls in the same change. That would allow hook, cancellation, resume, save and alarm races that the durable host explicitly asks its caller to serialize.

## Exact blocking paths

`apps/cloud/src/workspace.ts:102-109` chains each operation onto `serial`. The tail settles after either success or failure, so an exception does not permanently poison the queue. `fetch` places its entire callback on that chain at lines 112-180. `alarm` places the whole awaited scheduler tick on the same chain at lines 183-186. There is one queue per Workspace instance, not one global queue across workspaces.

Every fetch waits before even checking `X-Loopy-Workspace`. GET, HEAD, invalid requests, status and artifact export requests all enter the queue. A request that arrives behind a tick waits for the remaining tick and every earlier operation. A slow read also delays later mutations and alarms.

An alarm tick holds that queue through all of the following:

- `scheduler.ts:180-188` awaits the recovery alarm write, due schedules and release of suspended owners. `scheduler-schedules.ts:47-50` loads each due schedule's saved graph through the R2 registry before validating and firing it. The due schedule scan is bounded at 32 rows, but those loads run sequentially.
- `scheduler.ts:190-227` processes candidate runs sequentially. Each candidate awaits `registry.revisionGraph` at line 207, then the whole `activateDurable` call. `artifacts.ts:142-152` reads and validates the graph; `artifacts-storage.ts:33-54` awaits R2 GET and its body, and graph revision validation also awaits hashing.
- `host/durable.ts:120-164` claims or heartbeats, commits reducer effects, then reconciles work. `host/durable-work.ts:39-69` awaits provider lookup and, when appropriate, provider start. `provider.ts:28-48` performs external HTTP with a five-second signal and reads and parses the response. `provider.ts:87-104` also retrieves code/parser bundles from R2 before POSTing an attempt.
- `scheduler.ts:229-242` prunes events, calculates the next wake and updates or deletes the alarm. Failures record the scheduler error and arrange recovery. These steps remain inside the same queued turn.

`maxWork:16` at `scheduler.ts:213` bounds reconciliation units for each candidate. It is not a five-second wall-clock bound for the whole tick. Multiple candidates, multiple provider calls, schedule graph loads and other R2 work can occur in a turn. Reducing `maxWork` or provider timeouts is a separate policy change, not proof that reads are safe to separate.

Fetches can also hold the queue on external work:

- Save validates artifacts, measures existing graph sizes, uploads bundles/source/graph, then publishes SQL metadata. See `artifacts.ts:191-210` and `artifacts-capacity.ts:16-40`.
- Current graph/source and historical graph/source requests await R2. Cold summary reads also fetch graphs and repair SQL metadata. See `artifacts.ts:40-123`, `service/queries.ts:83-92`, and `service/service.ts:74-92`.
- `GET /api/cloud/artifacts` calls `artifactResponse` inside the queue at `workspace.ts:163-169`. That handler reads the run, requires a matching workspace and terminal run, then awaits the provider at `artifact-route.ts:35-48`. `provider.ts:60-84` uses an external artifact GET with a 15-second signal and bounded response parsing.
- Non-GET/HEAD requests await `scheduler.wake` before dispatch at `workspace.ts:158-160`. Preserve that ordering and its current error behavior in a read-only separation.

SSE has an important limit. The queue covers `eventStream` cursor validation and initial transaction validation until it returns a Response, `service/events.ts:26-52`. It does not hold the queue for the stream lifetime. Subscription callbacks and later flush, decoration and delivery already occur outside that fetch callback, at lines 159-208. Moving SSE setup is not needed to stop an open stream from owning the queue.

## Reads and consistency

### SQL-only reads suitable for a first separation

`DurableSqlDriver` consumes SQL cursors synchronously before any await and maps transactions to `storage.transactionSync`, `sql-driver.ts:11-35`. The methods below have no asynchronous gap inside their actual SQL collection. Their `async` return type does not make the SQL work asynchronous. A read can observe an earlier committed state while a scheduler is awaiting a provider; it must never see half an `apply` transaction.

- Event history list, `GET /api/event-history`, delegates to `eventPage`, `service/queries.ts:64-65`. Its candidate rows, bounds and page are collected without awaits in `store/sqlite/query-feeds.ts:119-163`. It performs no run-view decoration, registry call or repair. This is the measured `events` endpoint, distinct from SSE `/api/events` and event detail.
- Cursor, `GET /api/cursor`, delegates to `eventCursor`, `service/run-views.ts:189-190`. Epoch and sequence are captured together by a synchronous transaction, `store/sqlite/events.ts:55-73`.
- Other eligible leaf candidates are `/api/overview`, `/api/logs`, `/api/logs/:id`, `/api/schedules/overview`, `/api/schedules`, and run payload, logs, execution page/detail, scope counts and scope items. See `service/routes.ts:141-168`, `service/queries.ts:14-60`, `service/service.ts:95-118`, `service/schedules.ts:22-35`, and `store/sqlite/query-{runs,nodes,feeds}.ts`. Run-scoped handlers have an awaited existence/reference check before collection. The current API has no run deletion path; the reference fields used here are immutable. Their returned data comes from one synchronous collection, not a captured run status decorated later.

The last group is source-supported as a later allowlist expansion, not part of the proposed two-route minimum. In particular, multi-statement `scopeItems` and execution detail are synchronous collections on this DO driver, not a portable promise of transaction isolation for an arbitrary future async backend. Keep the proposal scoped to Workspace and this driver. Preserve response schemas, preview caps, scan bounds and cursor behavior.

Allowing reads changes ordering: a new read may return committed state before a queued mutation runs, even if that mutation reached Workspace first. It may also observe a valid intermediate commit within a scheduler activation. A mutation's completed HTTP response followed by a new read should still expose its committed changes. If callers require all reads to wait behind previously admitted mutations, an unconditional bypass cannot preserve that contract. Add that requirement explicitly before expanding the change; the current queue supplies it incidentally.

### Composite reads that should remain serialized initially

`/api/runs` first collects run rows, then awaits registry summaries, then fetches current pending hooks. `service/run-views.ts:53-97` shows those separate stages. A concrete proposed-race witness is a `waiting=true` query selecting a suspended run, cold summary I/O holding the request, and a hook resolution or expiry completing before `pendingHooks`. The final view can combine the old selection/status/owner with a newer wait state. Capturing an old run and computing `ownerStale` using a later clock also changes what that field means near lease expiry. These are reasons to test and define the contract, not claims of a reproduced defect.

`/api/loopies` collects workspaces, schedules and grouped counts, loads the catalog, and then queries recent runs for each definition, `run-views.ts:100-167`. Registry awaits allow writes between the counts and recent-run queries. A response can report counts from before a completion while including that completion as its latest run. Request-local catalog caching avoids duplicate reads; it does not provide a database snapshot.

`/api/runs/:id` has an atomic store snapshot but is not entirely atomic as returned over HTTP. `store/sqlite/query-nodes.ts:145-177` captures the run, nodes, waits, scope counts and event cursor together in one transaction. `run-views.ts:170-177` then replaces the run with an asynchronously decorated view. That view consults registry summaries and current pending hooks. If moved unchanged, its `waitingOn` could describe a later state than the snapshot's hooks and replay cursor. Keep the store transaction. Do not mistake it for a transaction around the whole HTTP response.

Before separating these routes, capture all mutable SQL inputs for each response coherently without an external-I/O transaction. For a snapshot, derive pending-wait and owner fields from the captured state and one chosen observation time, then attach definition description without re-reading mutable execution state. Preserve the current definition-description policy, which uses the current definition rather than the run's pinned revision. For loopies, grouped counts, schedules and selected recent runs need a common capture if exact mutual consistency is required. For runs, selection and pending-hook state need the same capture. This is additional service/store work and should be reviewed separately from the two-route Workspace change.

Event detail can decorate a historical run event through `ServiceRunViews.resolve`, `queries.ts:67-81`. SSE does the same for run events and has multi-await cursor/replay validation. Keep their setup serialized initially and test replay races before widening the allowlist. SSE's existing asynchronous delivery is not evidence that every other composite read is safe.

Cloud status awaits `getAlarm` before selecting turn errors and the scheduler error, `workspace.ts:143-155`. Daemon status reads running count and next wake separately, `service/routes.ts:177-183`. Both are composite diagnostics. Their method behavior also differs: cloud status currently intercepts its path without a method restriction, whereas normal routes match an exact method. Leave them alone in the minimum proposal.

### Registry CAS and R2 races

Summary reads are not literally read-only. `R2ArtifactRegistry.resolveSummary` can load an old graph and call `ArtifactDefinitions.repair`, `artifacts.ts:63-110`. Repair rechecks the current generation and existing projection inside `transactionSync`, `artifacts-definitions.ts:118-129`. A stale read cannot overwrite a replacement's summary. The eight-attempt bound and shared byte budget must stay intact. Missing/corrupt old graphs only retry against a changed generation; unchanged missing/corrupt graphs still fail. Warm summaries skip R2 entirely.

These guards support concurrent single-summary repair in principle. They do not make a catalog list a snapshot, and they do not make runs/hooks/counts atomic. Existing workerd summary tests exercise replacement against valid, missing and corrupt old graphs, plus SQL rollback and warm reads, `definition-summaries-workerd.test.ts:94-293`. Those are source-inspected tests, not tests run by this lane, and they do not exercise a changed Workspace queue.

R2 publication has a different safety mechanism. `ArtifactStorage.put` uses a create-only condition, `artifacts-storage.ts:29-30`. Save writes artifacts before publishing a generation-checked SQL pointer and summary in one transaction, `artifacts.ts:191-210` and `artifacts-definitions.ts:140-187`. Graph/source reads capture a revision before reading its bytes. A concurrent replacement can therefore return the older captured revision with its matching bytes, which is coherent if that read policy is accepted. Do not re-read a newer pointer and label old bytes with it. Run graph/source must keep using the run's pinned revision.

No source conclusion here proves remote R2 behavior or cleanup safety under arbitrary deletion. This registry exposes no delete method. Missing/corrupt objects, conditional puts, per-workspace prefixes, graph hashes, source revision checks and size limits remain proof obligations for any later R2-read separation. Leave those routes queued for the first change.

### Artifact export has durable mutations

Artifact export is a GET at the public boundary, but downstream it acquires and releases durable export guards and creates/removes a helper. `apps/sandbox/src/attempts.ts:137-169` requires a finished receipt and tracks the operation. `attempt-exports.ts:95-129` reconciles guards, calls `beginExport`, reads the artifact and releases only after cleanup. `artifacts.ts:94-222` checks active mounts, runs a read-only helper and confirms its removal.

`apps/cloud/src/receipts-authority.ts:90-165` checks the current session, requires a finished attempt, excludes pending/busy work on the volume, and records an active guard transactionally. Admission also checks volume busy at lines 25-47. `endExport` checks the current caller session even when clearing an older guard; `AttemptExports.release` passes its current session at line 54. These guards belong to a separate receipt authority, outside Workspace's promise queue. They must remain authoritative if export ever moves, and a timed-out client must not imply cleanup or guard release.

The existing guard design is a reason a future export separation may be possible. It is not a reason to place export in the SQL-only allowlist. Keep it serialized now. Any later move needs concurrent export/admission, session replacement and failed-cleanup proof against the actual authority. Provider HTTP alone with a fabricated artifact response cannot prove those properties.
